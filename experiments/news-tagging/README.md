# Feeds Fun 语义打标适配试验

本试验使用通信与数据中心、汽车的 48 篇冻结新闻。标签流程参考 Feeds Fun，`@tag` 提取器按 BSD-3-Clause 许可从其 Python 函数移植，来源与修改记录见 [UPSTREAM.md](UPSTREAM.md)。

## 流程

1. 从既有冻结批次读取标题、链接及原文，沿用项目中的两项业务产品目录。
2. 将完整原文分块，保留少量重叠上下文，记录每块范围与处理状态。本批为 48 篇、124 块。
3. 将每块正文切成带编号的原文句子。GitHub 运行器内的模型只输出事件类型、事实状态、内容类型和原文句子编号，不接收产品目录，也不判断立讯供货或产品因果关系。
4. 程序按编号取回原句并校验编号存在，再将原始标签转为统一的小写连字符形式。候选新标签限于事件与内容类型，需人工核对。候选标签无效或与现有标签重复时只舍弃该候选并记录警告，不丢弃已有有效事件；核心事件的无效证据仍会使分块失败。
5. 合并各块标签，并与现有两项业务知识库的筛选结果交叉核对。仅完整处理的文章参与分歧和扩增统计；事件信号与筛选结果不一致时仅提示人工复核，不自动入选或修改知识库。

标签定义位于 `taxonomy.json`，模型提示词位于 `system-prompt.txt`。内容类型覆盖公告、业绩披露、技术分析、市场研究、评测、教程、促销、观点、访谈、展会、标准、研究专利和汇编等。事件还覆盖认证、部署、产能迁移、标准互操作、质量召回、安全事件、业务退出等。

## GitHub Actions 运行

工作流为 `.github/workflows/news-tagging-shadow.yml`。推送到 `codex/news-tagging-shadow` 分支且涉及试验文件时触发首次试跑，并保留 `workflow_dispatch` 入口。GitHub 手动工作流的可用性取决于工作流是否已出现在默认分支，首次独立分支试跑使用该分支的推送触发。

使用标准 Ubuntu 运行器，当前模型为 Qwen2.5-7B-Instruct 的 Q4_K_M 量化版本，推理引擎为 llama.cpp b6000。版本、两个分片文件的 URL 和 SHA-256 校验值位于 `runtime.json`，下载后逐个验证。模型文件合计约 4.7 GB，只存在于一次性的云端运行器中；不会下载 1.5B 模型，也不会占用用户电脑空间。公开仓库的标准 GitHub Actions 运行器目前免费。输出制品保留 3 天，缓存只保存成功的文本响应，并使用 7B 专属缓存前缀以隔离旧模型结果。

运行入口只访问运行器内部 `127.0.0.1:8080` 的模型。模型下载、健康检查和逐块推理失败均显示具体状态，并逐段打印进度。每次推理最多 600 秒，推理总预算为 300 分钟，作业总上限为 360 分钟。预算耗尽后保留已经验证的结果及缓存，后续试跑可继续处理。

工作流使用 `contents: read`，结果通过 Actions 制品提供下载。文件包括 `tags.csv`、`comparison.csv`、`results.json`、`report.md`、`tag-discovery.json`、`model-comparison.json`、`model-comparison.csv`、`model-comparison.md`、输入清单、运行状态和推理日志。对照 JSON 保留两模型逐篇的事件标签、证据原句和处理状态，便于程序读取；两次都完整处理的文章才统计标签增减。页面发布与人工核验可继续使用既有流程。

## 本地检查

```sh
node experiments/news-tagging/test.mjs
node experiments/news-tagging/test-model-comparison.mjs
node experiments/news-tagging/run.mjs --prepare
```

`--prepare` 仅输出 `outputs/news-tagging/manifest.json`，状态为 `prepared_for_inference`。`run-state.json` 记录当前运行状态，作业摘要通过运行时间与配置标识核对本次报告。本机配置对应模型服务器后，可以运行不带 `--prepare` 的入口。输出目录可通过 `NEWS_TAGGING_OUTPUT` 指定，输入冻结批次可通过 `NEWS_TAGGING_INPUT` 指定。

1.5B 模型的最近一次基线来自 GitHub Actions 运行 `42169329227`：48 篇、124 段，119 段校验通过，43 篇完整，耗时约 34.4 分钟。原始 `results.json` 保存在 `baselines/qwen2.5-1.5b-run-42169329227.json`，SHA-256 为 `a1afd78a7f9eb31660a37a23cdd4b4b9924b656216429ed39d4a2ba81c0e0111`。这保留了逐篇事件、证据和处理状态，供 7B 在相同 48 篇上的对照。两模型的标签差异不等于准确率提升，仍需按原文核查误判和漏判。旧模型输出不会参与 7B 推理或覆盖当前结果。

## 如何决定扩增标签

人工复核基准位于 `human-audit-48.json`，逐篇保存建议事件、阶段、业务链、首页去向和修订依据，来源为用户提供的 48 篇评审表。运行 `node experiments/news-tagging/evaluate-human-audit.mjs path/to/results.json > evaluation.json` 可生成逐篇缺失/多余标签及汇总。旧 7B 输出与人工建议仅有 5/48 篇事件标签集合完全相同，说明成功运行和证据句编号有效并不代表分类准确。该基准只用于评估，不自动覆盖原筛选决策或证明立讯供货。提示词已按人工定义收紧事件门槛；必须重新推理并与旧结果对照，不能用旧缓存证明新规则有效。

- 先看 `report.md` 的事件与内容覆盖，检查文章事件遗漏是否源于模型能力、提示词或证据不足。
- 查看候选标签的原文、涉及文章数和现有类别。重复描述或同义词优先合并，具有独立业务意义的新概念再加入分类。
- 多篇不同事件反复出现同一新概念时提高审阅优先级，单篇重大业务事件也可以提出新类别。
- 本批未出现的标签保留为覆盖信息。后续用新日期或来源验证类别是否仍有需要。
- 引用存在性校验只确认文本来源，语义对应和因果方向仍需人工审阅。现有人工审阅表继续作为准确率和召回率的依据。

当前产出为并行打标对照结果。每行保留既有系统结果，方便审阅标签带来的新增信息。

`comparison.csv` 逐篇并列原筛选结果与事件信号，标出需人工核查产品关联的文章。事件信号不等于立讯业务关联。`diagnostics.txt` 记录云端运行到达的阶段，`report.md` 给出未完成原因统计。
